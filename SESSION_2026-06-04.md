## Admin PIN — Invalid PIN silently fails (#1)

**Status:** 🔴 Bug — needs fix  
**Files:**
- `apps/web/src/lib/api.ts:56-71` — response interceptor handles `ADMIN_PIN_REQUIRED` but **not `ADMIN_PIN_INVALID`**
- `apps/web/src/components/admin-pin-modal.tsx:37-50` — submits PIN to store, no server-side validation on submit
- `apps/api/src/common/guards/admin-pin.guard.ts:47-53` — throws `ADMIN_PIN_INVALID` 403 on wrong PIN

**Problem:** When a wrong PIN is entered in the modal, it gets stored in the Zustand auth store. The next admin API request sends it via `x-admin-pin` header, gets 403 `ADMIN_PIN_INVALID`, but the frontend response interceptor only handles `ADMIN_PIN_REQUIRED`. The request silently fails, and the user is stuck with a bad PIN in the store until they navigate to security settings to clear it.

**Fix needed:**
1. In `api.ts` response interceptor, catch `ADMIN_PIN_INVALID`, clear `adminPin` from auth store, re-dispatch `admin:pin-required` event, and show an error.
2. In `admin-pin-modal.tsx`, add an error state that shows when the PIN was rejected by the server.

## Cancelled deposit not updating Deposit Credit tab until refresh

**Status:** 🟡 Needs investigation  
**File:** `apps/web/src/app/(dashboard)/wallet/page.tsx:218-227`

**Problem (reported by co-admin):** After cancelling a pending deposit, the Deposit Credit tab still shows the pending deposit banner/order. The user must refresh the browser to see the updated state.

**Current code:**
```tsx
useSocketEvent('deposit:updated', (payload) => {
  if (depositResult?.deposit.id === payload.depositId &&
      (payload.status === 'COMPLETED' || payload.status === 'CANCELLED' || payload.status === 'FAILED')) {
    resetDeposit();
  }
  void queryClient.invalidateQueries({ queryKey: ['wallet', 'deposits'] });
  void queryClient.invalidateQueries({ queryKey: ['wallet', 'me'] });
});
```

**Root cause hypothesis:** If `depositResult` is `null` (e.g., the user refreshed the page after creating the deposit), the `resetDeposit()` call is skipped. The query invalidation should refresh the deposit history list, but the **sticky "Resume pending PayMongo payment" banner at line 536** is derived from `depositHistory?.items.find(...)` — this should update when the query refetches. If it doesn't, the query might be stale or the socket event isn't reaching the listener.

**Fix needed:** Add logging to verify the socket event fires. Ensure the `depositHistory` query refetches correctly. Consider adding a `useEffect` watcher on `depositHistory` that auto-clears `depositResult` when no pending deposits exist.
