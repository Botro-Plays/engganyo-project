## Confirmed code findings

Line references below refer to the local June checkout unless stated otherwise. Unchanged files have the same lines at the fetched head. Findings are code-path conclusions, not attacks executed against a live service.

### A01 — Critical: temporary two-factor token accepted as API access token

Evidence: `apps/api/src/modules/auth/two-factor.service.ts:70` signs `{ sub, purpose: 'two_factor_auth' }` with `jwt.accessSecret`. `apps/api/src/modules/auth/strategies/jwt.strategy.ts:21-25` verifies that same key, then looks up the user by `sub` and reconstructs their role. It does not require an access-token purpose or reject the two-factor purpose. `JwtAuthGuard` delegates to this strategy.

Impact: after the password stage, a client can present the temporary token to normal protected API routes without completing the second factor. AdminTwoFactorGuard checks whether 2FA is configured, rather than whether this login completed it. An optional configured admin PIN remains a separate barrier on routes that enforce it.

Fix: separate keys and explicit token audiences/purposes for access, refresh, OAuth state, and two-factor challenges; reject all wrong-purpose tokens in HTTP and sockets. Add a regression test proving a two-factor challenge gets 401 on normal protected routes, including admin routes. Invalidate outstanding tokens after the fix.

### A02 — Critical: PayPal order amount and deposit binding are client-controlled

Evidence: `apps/api/src/modules/paypal/paypal.controller.ts` forwards `depositId`, `amount`, and `currency` from an inline body object without passing the authenticated user to `createOrder`. `paypal.service.ts:68` sends that amount to PayPal and attaches the order to the supplied deposit ID. At `:210-218`, capture detects a different paid amount but only logs a warning before completing the deposit. The already-captured recovery and completed webhook paths also need equivalent payment reconciliation.

Impact: an authenticated user can request an underpriced order against a higher-credit deposit. The code then awards the deposit's configured credits despite underpayment. Knowledge of another deposit ID also allows unauthorized order rebinding. Currency and method binding are not established by this endpoint.

Fix: derive amount and currency from an owned, eligible PAYPAL deposit on the server. Reject all mismatches; verify merchant, order/reference, currency, paid amount, and final captured state in every completion path. Use validated DTOs and stable gateway idempotency keys. Test underpayment, wrong owner/currency/method, duplicate completion, and recovery paths.

### A03 — High: proof downloads do not authenticate or authorize the reader

Evidence: `apps/api/src/main.ts:65-73` only checks that Authorization starts with `Bearer `. Any following text passes. Static assets are served after that middleware, outside the controller JWT guard. No owner, campaign-reviewer, or admin authorization check follows. `infra/nginx/nginx.conf:105-116` adds public immutable caching to all uploads, including proofs, conflicting with API private-cache intentions.

Impact: someone who obtains a proof URL can fetch it with an arbitrary Bearer value. Public cache headers can further expose sensitive proof files. URL unpredictability is not authorization.

Fix: serve proofs through a real authenticated, resource-authorized endpoint or narrowly scoped expiring signed URLs. Separate avatar and proof proxy locations; proofs should not have public caching. Check that legitimate image previews can supply the chosen authentication mechanism.

### A04 — High: proof upload path traversal and untrusted file extension

Evidence: `uploads.controller.ts:68-75` joins the unvalidated body `taskId` into a filesystem path. Both upload handlers retain the original extension and trust the client-declared MIME type, without decoding or re-encoding the image.

Impact: a signed-in caller can use parent path segments to escape their assigned proof directory and place files in other writable locations. A claimed image can carry a non-image extension/content; placement beneath a public upload location increases stored-content risk. Random filenames limit precise overwrite attacks but do not prevent directory escape.

Fix: use a validated task identifier, verify task assignment/ownership, derive storage paths server-side, enforce resolved containment, decode/re-encode accepted images, and select the output extension from verified content. Keep temporary files outside the publicly served uploads tree.

### A05 — High: deposit completion can lose concurrent wallet updates

Evidence: `wallet.service.ts:541-605` reads a wallet balance, computes `balanceAfter`, and writes `balance: balanceAfter` without a version predicate or wallet row lock. The conditional deposit update prevents duplicate completion of the same deposit, but does not serialize different deposits or other wallet operations.

Impact: two deposits for one wallet, or a deposit racing another balance change, can overwrite a balance while both ledger entries commit. A transaction alone does not prevent this at the default isolation level.

Fix: use the transaction-aware optimistic wallet helper added by Jhing, or lock the wallet before reading and recording balances. Keep deposit transition, wallet, ledger, and mirrored user balance in one transaction. Test distinct simultaneous deposits and deposit-versus-spend.

### A06 — High: campaign review and cancellation have duplicate reward/refund races

Evidence: `campaigns.service.ts:342-410` reads SUBMITTED before opening the transaction, then updates by ID without a status predicate and credits after that transaction. `:513-569` reads cancellable status and task count, updates by ID, and credits the refund separately.

Impact: concurrent approvals can both pass the initial check, increment slots twice, and pay twice. Concurrent cancellations can both refund. A wallet failure after status commit can instead leave a verified task unpaid or a cancelled campaign unrefunded. Creation also debits before campaign creation (`:197-202`).

Fix: conditional status claims and wallet changes in one transaction, with unique business-operation references. Serialize cancellation against task assignment and calculate refundable slots under the same lock. Test repeated/concurrent approval, rejection, cancellation, assignment, and downstream failure.

### A07 — High: tips, rain, purchases, and task rewards cross transaction boundaries

Evidence: `channels.service.ts:544-568` debits sender then credits recipient separately; rain does the same per recipient (`:758-764`). `store.service.ts:236-328` debits before its inventory transaction and relies on a best-effort refund if that fails. `tasks.service.ts:445-489` and `:596-635` commit completion changes before wallet rewards.

Impact: failures can lose credits, partially distribute rain, or mark tasks rewarded without actually paying. A process exit between store debit and inventory creation is not caught by the refund block.

Fix: share one database transaction per business operation using the new optional wallet transaction client. Add durable idempotency/reconciliation for operations crossing external services. Test failures between each side of transfers and reward delivery.

### A08 — High: declared auth/store throttles are not enforced by guards

Evidence: `app.module.ts` configures ThrottlerModule but no ThrottlerGuard/APP_GUARD is registered anywhere in `apps/api/src`. Store purchase has `@Throttle`, without that guard. Auth register has `@UserRateLimit`, but AuthController only attaches JwtAuthGuard; UserRateLimitGuard is not attached there. Nginx's stricter auth location is `/api/v1/auth/`, while the API's actual prefix is `/api/auth/`.

Impact: the intended app-level limits do not run on these routes. Nginx still supplies its general API limit, but its stricter auth limit is bypassed by normal routing. Published API ports also allow proxy bypass if reachable. Do not rely on the June audit's claim that the store decorator alone proves throttling.

Fix: attach the appropriate guards, use version-correct throttle time units, correct Nginx paths, enforce login and 2FA attempt limits, and test actual 429 responses. Trust only known proxy hops and derive client IP consistently.

### A09 — High: sockets retain stale account privileges

Evidence: `events.gateway.ts:81-108` verifies the token at connection and uses its role to join the admin room. `channels.gateway.ts` stores the role from the handshake and reuses it for later messages. Neither path rechecks current account status or disconnects at token expiry.

Impact: suspended or demoted users can retain socket access; a connection may remain active beyond token expiry. HTTP cache invalidation in admin status/role updates does not remove existing socket memberships.

Fix: share access-token purpose validation and current account checks with HTTP, enforce expiry, and disconnect/re-authorize sockets when account permissions change. Test demotion, suspension, logout/revocation policy, and expiry on established connections.

### A10 — Medium: frontend retries unsafe mutations automatically

Evidence: `apps/web/src/lib/api.ts:55-85` retries network errors and 5xx responses three times, regardless of HTTP method. This remains in the fetched head.

Impact: a server may commit a purchase, tip, or campaign before a response is lost. Replaying that POST can repeat it, amplifying missing idempotency and race protections.

Fix: retry reads by default; only retry mutations with server-enforced idempotency keys. Test a committed request whose response is lost.

### A11 — Medium: non-active account states pass JWT authentication

Evidence: `jwt.strategy.ts` rejects BANNED and SUSPENDED, but accepts DEACTIVATED and PENDING_VERIFICATION in both cached and database branches. Registration creates an access token even when email verification is enabled and initial status is PENDING_VERIFICATION.

Impact: email verification and deactivation do not consistently block protected API access.

Fix: require ACTIVE for normal protected routes, with explicit exceptions for verification/recovery. Apply the same policy to refresh and sockets and test each state.

## Infrastructure and delivery findings

### I01 — Critical exposure if reachable: Redis is published without authentication

`docker-compose.yml:34-45` publishes Redis on all host interfaces and sets no requirepass/ACL. PostgreSQL, API, and web are also published on all interfaces. The database password has a development fallback. This is configuration evidence; actual Internet reachability was not tested and depends on provider/host firewalls.

Redis contains security-relevant caches and job queues, not just disposable page data. Restrict services to the internal Docker network; use loopback binds only for intentional local administration. Require configured database credentials and use Redis authentication as defense in depth. Verify the provider firewall and Docker-published ports explicitly. Do not infer the old host's corruption was caused by this finding.

### I02 — High: JWT defaults are accepted in production

`config/jwt.config.ts` falls back to known development access and refresh secrets; ConfigModule has no production environment validation. `DEPLOYMENT.md:48` incorrectly tells operators to set JWT_SECRET, which the JWT configuration does not read. The production example does list the correct separate variables.

Require strong, distinct JWT_ACCESS_SECRET/JWT_REFRESH_SECRET at startup and reject development/placeholder values. CryptoUtil already correctly rejects invalid ENCRYPTION_KEY; apply comparable startup validation to other required settings. Seed has a documented default admin password; production seeding must fail when a real password is absent.

### I03 — High: recovery/deployment instructions cannot bootstrap as written

DEPLOYMENT steps 4-6 start only postgres/redis and then use `compose exec api`, although api does not exist yet. Use a one-off API container with an explicit entrypoint for migrations, then start the app. The API entrypoint already runs migrations before startup. Seeding is an intentional fresh-install operation, not a substitute for restoring user data.

Preserve/restore database backups, uploads, environment configuration and encryption key material. Git and Docker images do not contain old user balances or uploaded proofs. Replacing encryption keys without a data migration can make restored OAuth and 2FA secrets unreadable.

### I04 — Medium: deployment can report success without a healthy app

The workflow continues after its API health timeout, runs migrations after startup despite entrypoint migration, and has no final mandatory API/web health assertion. It deploys mutable `latest` images and runs `git pull origin main`, so the checked-out code/config and pulled image may differ from the triggering commit.

Deploy one immutable commit/image digest, fail on health timeout, perform a final health check, and maintain an explicit rollback plan accounting for schema changes. Manual dispatch is now required for publishing/deployment; pushes still run CI/E2E. No actual CI result was verified in this audit.

### I05 — Medium: container builds do not use the committed monorepo lockfile

API Dockerfile uses an app subdirectory context and `npm install`. The tracked lockfile is at repository root; the workflow builds each app with its subdirectory as context. This makes production dependency resolution drift from the root lockfile audited here. Use a workspace-aware build context and deterministic lockfile installation. Container image dependency scanning is still required.

### I06 — Medium: Redis eviction policy mixes cache and durable work

Compose uses `allkeys-lru` for the Redis instance shared by caches and queues. Memory pressure can evict queue, rate-limit, and session-related keys. Separate cache and queue/security workloads or select a queue-appropriate no-eviction configuration with monitoring. Verify queue library/operational documentation: code uses `@nestjs/bull`, while comments and some docs call it BullMQ.
